# Creating New Lab

When adding a new lab, follow the existing lab structure and keep the change scoped to the new route, feature folder, data, and navigation registration.

1. Choose the parent section slug and lab slug in kebab-case, for example `hooks-effects` and `debounce-throttle`.
2. Add a route file under `src/routes/_dashboard/{section}/{lab}.tsx` that imports the page component from the matching feature folder and uses `createFileRoute`.
3. Create the feature folder at `src/features/{section}/{lab}/`.
4. Add a `{PascalCaseLabName}Page.tsx` file for the lab screen.
5. Add a `{lab}.data.ts` file for static concepts, examples, code snippets, lists, and reusable copy.
6. Add small lab-only components inside the lab feature folder when they are not broadly reusable.
7. Register the lab card in `src/content/labs.ts` with `id`, `title`, `description`, `level`, `section`, `sectionLabel`, `href`, `imageSrc`, and `imageAlt`.
8. If the parent section page has its own `*.data.ts` lab list, add the new lab there too.
9. Do not manually edit `src/routeTree.gen.ts`; it is generated by TanStack Router tooling.

Prefer this file layout for nested labs:

```text
src/routes/_dashboard/{section}/{lab}.tsx
src/features/{section}/{lab}/{PascalCaseLabName}Page.tsx
src/features/{section}/{lab}/{lab}.data.ts
src/features/{section}/{lab}/{OptionalLocalComponent}.tsx
```

For a parent section page, follow this pattern:

```text
src/routes/_dashboard/{section}.tsx
src/features/{section}/{PascalCaseSectionName}Page.tsx
src/features/{section}/{section}.data.ts
```

Lab pages should usually include:

- `RouteBreadcrumbs` near the top.
- A clear page title and section badge.
- A concise learning description.
- Interactive examples when the concept benefits from direct manipulation.
- Code examples loaded from the lab data file instead of long inline strings in JSX.
- Responsive layout using existing Tailwind patterns.

Reuse shared components before adding new ones:

- `src/components/shared/lab-card`
- `src/components/shared/lab-topics-section`
- `src/components/shared/route-breadcrumbs`
- `src/components/ui`

Run verification after adding or changing a lab:

```bash
npm run lint
npm run build
```

## External Resources

Use external resources to verify facts and APIs, but let this repository's existing patterns be the primary guide.

- Prefer local code patterns before copying external examples.
- Use official docs for React, TanStack Router, Vite, TypeScript, Tailwind CSS, browser APIs, accessibility, and performance.
- Use the shadcn MCP for shadcn/ui component examples, install commands, and expected composition.
- Use MDN for web platform behavior and browser APIs.
- Use web.dev or official framework documentation for performance guidance.
- Check `package.json` before following docs so examples match the installed libraries.
- Avoid random blog snippets as primary references; use them only as supporting context when official docs are missing a practical example.
- For current or changing information, verify with a current source before implementing.

## Repo Conventions

- Keep feature code under `src/features/{section}` and route files under `src/routes/_dashboard`.
- Keep static lesson content, code samples, concept lists, and card data in `*.data.ts` files.
- Keep shared UI generic. If a component only makes sense for one lab, leave it inside that lab folder.
- Use existing shadcn/ui primitives from `src/components/ui` instead of creating new primitive components.
- Use `lucide-react` for icons.
- Keep pages responsive on mobile and desktop; avoid layouts that require horizontal scrolling except for code blocks.
- Keep copy concise and instructional. Labs should teach through examples, not long exposition.
- Use accessible labels for inputs, controls, and interactive examples.
- Preserve the existing import alias style with `@/`.
- Do not introduce a new state, styling, routing, or component library unless the task explicitly requires it.

## Visual And UX Guidance

- Build the actual lab experience as the first screen, not a marketing-style landing page.
- Prefer dense, scannable educational UI with clear controls and immediate feedback.
- Use cards for repeated examples, framed tools, or grouped content; avoid deeply nested cards.
- Keep code examples readable with horizontal overflow on small screens.
- Use generated SVG data images in `src/content/labs.ts` when adding lab card artwork, matching the existing simple line-art style.

## Validation

- Run `npm run lint` for formatting and static checks.
- Run `npm run build` to verify TypeScript, route generation, and production bundling.
- For substantial UI changes, start the dev server and inspect the affected route in the browser.
